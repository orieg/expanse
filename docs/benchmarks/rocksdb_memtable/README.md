# RocksDB MemTable suite: results and how to read them

*(measured: reference host — Intel i9-12900F, 8P+8E / 24 threads, 30 MiB L3, `Linux-6.8.0-136-generic-x86_64-with-glibc2.35`, commit `7cd5140e`; pin `0-15`; `benches/bench_memtable.cc` built `-O3` against release `libexpanse.so`; 100,000 keys, 16-byte key, 64-byte value payload; **two independent runs**, [35547165132](https://github.com/orieg/expanse/actions/runs/35547165132) and [35547235205](https://github.com/orieg/expanse/actions/runs/35547235205), 5 rounds and 13 cells each, driven by [`scripts/single_threaded_bench.py`](scripts/single_threaded_bench.py) — one `bench_memtable --arm <phase> --round N` process per cell, phases interleaved within each round — into [`results/baseline_rocksdb.json`](results/baseline_rocksdb.json) and [`results/baseline_rocksdb_run2.json`](results/baseline_rocksdb_run2.json). Every bracketed pair is a BCa 95% bootstrap interval (2,000 resamples, seed 42); each ratio is a **paired** one-sample interval over the per-round quotient subject/baseline measured in the same invocation, not a two-sample ratio of the two columns beside it. Peak foreign busy CPU was 0.14 core-equivalents in run 1 and 0.13 in run 2, against a ceiling of 1.0, and peak `load1` was 0.34 and 0.48 on 24 logical CPUs; per-cell snapshots are in each artifact's `provenance.loads`. SkipList arm = the fair variable-height baseline. Memory row: deterministic seeded byte accounting, identical in every round of both runs and byte-for-byte identical to the earlier measurement. `SkipListRep`/`VectorRep` are the in-file reference implementations, not stock RocksDB.)*

![RocksDB MemTable Benchmark: ExpanseMemTable vs SkipList vs VectorRep](results/bench_rocksdb.svg)

> **Baseline retraction ([#372](https://github.com/orieg/expanse/issues/372)), discharged.** Every "vs SkipList" cell below was once measured against a strawman skiplist whose nodes statically embedded the full 16-pointer tower (~146.7 B/entry). The density edge was corrected first — **1.42×**, not 11.11×, by deterministic byte accounting, and that figure is what the two runs above reproduce. The throughput rows were then re-measured against the fair variable-height baseline at commit `6cb64b45`, and every ratio moved down from the strawman run's; the fat-node layout had been degrading the skiplist's cache locality exactly as suspected. **Every wall-clock figure from that `6cb64b45` run is superseded by the table below**, and the figures it published — sequential scan `3.331×`, batch scan `2.524×`, point lookup `1.457×`, range seek `1.512×`, insert `1.406×` — are registered in [`.github/superseded-figures.json`](../../../.github/superseded-figures.json) so they cannot return unlabelled.
>
> **The re-measurement spans three changes at once, and no single one of them is attributed here.** Between `6cb64b45` and `7cd5140e` the engine changed ([#769](https://github.com/orieg/expanse/pull/769) and [#877](https://github.com/orieg/expanse/pull/877) rewrote the iterator and `ScanBatch`, and until #877 the batch-scan loop did not terminate at all, so the published `2.524×` was timing a loop that never completed a scan); the runner changed from a shell loop over `make bench` to the driver above, which moved the process boundary from one process per round to one process per phase per round; and the ratio estimator changed from a two-sample interval over the two arms' rounds to a paired interval over the per-round quotient. A difference against the `6cb64b45` figures therefore has three candidate causes and this suite has no instrument that separates them. Two earlier partial re-runs of the scan rows, at `2b4c15a8` (run [34715487558](https://github.com/orieg/expanse/actions/runs/34715487558)) and `314deb39` (run [34718103662](https://github.com/orieg/expanse/actions/runs/34718103662)), committed no artifact and are superseded by the pair above.
>
> **What both runs agree moved, against the superseded `6cb64b45` interval** (`docs/BENCHMARKING.md` rule 18: a delta is named only where both runs move the same way with intervals clear of the old one). Up: point lookup vs SkipList `1.457×` → **1.4915 / 1.4985**, point lookup vs VectorRep `2.072×` → **2.1191 / 2.1244**, insert vs VectorRep `0.0218×` → **0.0235 / 0.0234**. Down: **batch scan vs SkipList `2.524×` → 2.1376 / 2.1301 — a loss, and the largest movement in the table.** Everything else is not confirmed by both runs: the sequential-scan ratio (`3.331×` → 3.1426 / 3.0744) and the `Iterator`-vs-VectorRep ratio separate in run 2 only, the insert ratio vs SkipList (`1.406×` → 1.4734 / 1.4757) misses by 0.0005 on run 1's lower bound against the old upper bound, and both range-seek ratios and the batch-vs-VectorRep ratio overlap in both runs.
>
> **The batch-scan loss is a ratio falling while both sides got faster on the subject's side of it only in one run.** The `SkipListRep` scan arm rose in both runs and clear of its old interval, `46.29` → **56.29 / 59.35 Mops/s**; the `ScanBatch` arm's own figure rose to **119.69** in run 1, whose interval still overlaps the published `116.82`, and to **126.37** in run 2, which clears it. So the confirmed statement is that the baseline rose and the ratio fell; that the subject also rose is confirmed by one run of the two, and no mechanism is attributed to either — no counter was collected on these runs.

### How to read the results

Every figure below is run 1's, with run 2's beside it; a claim rests on both (`docs/BENCHMARKING.md` rule 18).

1. **Panel 1: Sequential Scan (`prefixscan`) — 3.1426× [3.1061, 3.2269], and 3.0744× [3.0480, 3.1095] in run 2**
   Traversing contiguous 64-byte leaf blocks via intrusive sibling leaf chaining achieves **176.62 Mops/s** [159.08, 182.81] against **56.29 Mops/s** [49.27, 58.67] for `ReferenceSkipListRep` (182.45 and 59.35 in run 2), eliminating pointer chasing along skip-list tower links *(workload: rocksdb_memtable_single_threaded)*. `VectorRep` scans at **630.21 Mops/s** as an unindexed flat array ceiling. The ratio is below the superseded `3.331×`, in run 2's interval only, so it is not restated as a confirmed change.
2. **Panel 2: RAM Footprint per Entry — 1.42× Higher Key Density (13.2 against 18.7 B/entry)**
   Expanse organizes entry pointers into dense 64-byte aligned blocks indexed by the digital trie, consuming 13.20696 bytes of metadata per key against 18.74416 bytes for the fair variable-height skiplist *(workload: rocksdb_memtable_single_threaded)*. `VectorRep` uses 10.48632 B/entry (single contiguous pointer array). Deterministic byte accounting: identical in all ten rounds across the two runs, which is why this row carries no interval (AGENTS.md §8.4).
3. **Panel 3: Point Lookup Latency (`readrandom`) — 1.4915× [1.4901, 1.4939], and 1.4985× [1.4913, 1.5073] in run 2**
   Bounded $O(k)$ trie descent followed by binary search within the target 64-byte leaf block puts random read latency at **261 ns** (3.8262 Mops/s) against **390 ns** (2.5653 Mops/s) for SkipList *(workload: rocksdb_memtable_single_threaded)*. This is the one vs-SkipList ratio that both runs move up and clear of the superseded `1.457×`. The `readrandom` hit rate is ~9%, not ~100%, because MVCC hides every entry newer than the query snapshot — see the workload-shape declaration in `benches/bench_memtable.cc`, which is what the ratio describes.

### Concurrent read scaling (#802)

*(measured: reference host — Intel i9-12900F, 8P+8E / 24 threads, 30 MiB L3, Linux 6.8; commit `0ed8f5e5`; pin `0,2,4,6,8,10,12,14`, one hardware thread per physical P-core, as pre-registered; `benches/bench_memtable_concurrent.cc`; 5 rounds per cell, 60 cells per run; **two independent runs**, [34775640656](https://github.com/orieg/expanse/actions/runs/34775640656) and [34775850899](https://github.com/orieg/expanse/actions/runs/34775850899); artifacts [`results/baseline_concurrent_reads_amended_h1.json`](results/baseline_concurrent_reads_amended_h1.json) and [`results/baseline_concurrent_reads_amended_h1_run2.json`](results/baseline_concurrent_reads_amended_h1_run2.json). Pre-registered in [`METHODOLOGY.md`](METHODOLOGY.md) §5 before the harness existed, amended in §5.9 before these runs were dispatched, outcomes in §5.10. A pair at the same commit and pin taken before the amendment is in §5.8, with artifacts [`results/baseline_concurrent_reads_pin_one_sibling.json`](results/baseline_concurrent_reads_pin_one_sibling.json) and [`results/baseline_concurrent_reads_pin_one_sibling_run2.json`](results/baseline_concurrent_reads_pin_one_sibling_run2.json). An earlier pair of runs at the same commit under the auto pin `0-15`, which is 8 P-cores with both SMT siblings of each, is in §5.7, with artifacts [`results/baseline_concurrent_reads.json`](results/baseline_concurrent_reads.json) and [`results/baseline_concurrent_reads_run2.json`](results/baseline_concurrent_reads_run2.json).)*

> **H1 and H2 pass; H3 is not evaluable.** Two earlier pairs of runs did not decide H1. The first used the auto pin `0-15` instead of the pre-registered one (METHODOLOGY §5.7). The second ran under the pre-registered pin and found the paced writer 42.4–44.6% short of its offered 250,000 inserts/s in H1's gate cell (`R = 7`) in every run. Because §5.5 never defines how short is too short, H1 was reported not gated (§5.8). The amendment in [`METHODOLOGY.md`](METHODOLOGY.md) §5.9 derives from the bound that no writer shortfall can move H1's decision off "the lock covers about half a read". It was pushed before the two runs below were dispatched. It was also written after the earlier data had been read, so it is not a blind pre-registration, and it stated in advance that H1 would pass. Under it, **H1 and H2 pass in both runs**. H3 is not evaluable, because `scripts/fit_usl.py` returns no usable `alpha` interval on this arm's curves. Full account: [`METHODOLOGY.md`](METHODOLOGY.md) §5.10.

`FindLeafBlockForSeek` takes the same `mutex_` that `Insert` holds for its whole body, so every read serialises on the writer's lock before it reaches the per-leaf seqlock. This arm measures what that costs.

Aggregate read throughput, Mops/s, mean of 5 rounds (run 1):

| writer | R=1 | R=2 | R=4 | R=7 | `S(7)` paired BCa 95% |
|---|---:|---:|---:|---:|---|
| **idle** (control) | 4.092 | 3.113 | 2.808 | 2.541 | **0.621** [0.611, 0.631] |
| **paced** (250k/s offered; 139,698–145,363 inserts/s achieved at `R = 7`, gated under §5.9) | 1.344 | 0.985 | 1.006 | 0.838 | **0.624** [0.618, 0.630] |
| free (reported, never gated) | 0.203 | 0.380 | 0.704 | 0.782 | 3.849 [3.729, 3.934] |

**Reads do not scale; they regress.** `S(7) < 1` means seven readers deliver *less* aggregate throughput than one. The idle control is what makes that attributable: with no writer at all, seven readers deliver 0.621× what one delivers [0.611, 0.631], so the serialisation is reader-against-reader, not reader-against-writer. Both gates pass in both runs: H1's paced `S(7)` upper bounds are 0.630 and 0.628 against 2.0, and H2's idle `S(7)` upper bounds are 0.631 and 0.614 against 3.5. That is METHODOLOGY §5.4's first row: the locate phase is the constraint, and a shared lock over it is the cheapest candidate. No such design has been built or measured.

**The free-writer cell is the one that looks like scaling and is not.** Its `S(7)` of 3.849 comes from starvation, not parallelism: a single reader against a free-running writer gets 0.203 Mops/s against the control's 4.092, and adding readers only recovers collectively what one reader could not take from the lock. It was pre-registered as never-gated for exactly this reason. It is also the one never-gated cell that moved with the pin, lower under the pre-registered pin in both runs, and the mechanism behind that is unmeasured (METHODOLOGY §5.8).

**What is not claimed.** No hardware counter was collected, so the mechanism behind the regression is unmeasured — `scripts/rocksdb_locate_bound.py` predicted a flat curve and its floor of `S = 1` is refuted, which means there is real cost (cache-line traffic on the mutex word, convoying, wake-up) that the derivation has no term for. H3, the check that the bound and a USL fit agree, is not evaluable on this arm (METHODOLOGY §5.10). No alternative design has been built or measured.

### Optimistic-seek arm (#802, #900 step 10)

*(measured: reference host — Intel i9-12900F, 8P+8E / 24 threads, `Linux-6.8.0-136-generic-x86_64-with-glibc2.35`; commit `d5839c01`; suite `rocksdb_concurrent_optimistic`, lock scopes `full`, `trie` and `opt` interleaved, `R` = 1, 2, 4, 7, 78 rounds per cell, 2.0 s window, paced writer offered 250,000 inserts/s, 1,872 cells per run; four runs in sequence, two per pin — [35040060624](https://github.com/orieg/expanse/actions/runs/35040060624), [35044889994](https://github.com/orieg/expanse/actions/runs/35044889994) under `0,2,4,6,8,10,12,14`; [35049520714](https://github.com/orieg/expanse/actions/runs/35049520714), [35054023609](https://github.com/orieg/expanse/actions/runs/35054023609) under `0-15`; artifacts [`results/baseline_concurrent_reads_optimistic_pin_one_sibling.json`](results/baseline_concurrent_reads_optimistic_pin_one_sibling.json), [`…_pin_one_sibling_run2.json`](results/baseline_concurrent_reads_optimistic_pin_one_sibling_run2.json), [`…_pin_0-15.json`](results/baseline_concurrent_reads_optimistic_pin_0-15.json), [`…_pin_0-15_run2.json`](results/baseline_concurrent_reads_optimistic_pin_0-15_run2.json); workload: `rocksdb_memtable_concurrent_read_scaling`; pre-registered in [`METHODOLOGY.md`](METHODOLOGY.md) §5.16 and §5.16.1 before any optimistic-seek code or cell, outcomes in [§5.17](METHODOLOGY.md#517-outcomes-of-the-optimistic-seek-arm); verdicts from `python3 scripts/rocksdb_locate_bound.py`.)*

`ExpanseMemTableRep::SeekLockScope::kOptimistic` takes no lock in a seek's locate phase: it reads the trie, an `expanse_sync_map_t`, through a per-thread reader handle. All four runs are admissible — `optimistic_problems` refuses none, peak foreign busy CPU was 0.09–0.20 core-equivalents and peak `load1` 3.46–3.68 on 24 logical CPUs, against ceilings of 1.0 and 12.

| pin | O1 idle `opt/full` | O2 idle `opt/trie` | O3 paced `opt/trie` |
|---|---|---|---|
| `0,2,4,6,8,10,12,14` | `BOUNDARY_RESULT` | `BOUNDARY_RESULT` | **`PASS`** |
| `0-15` | `BOUNDARY_RESULT` | `BOUNDARY_RESULT` | **`PASS`** |

**O3 passes under both pins; O1 does not, so [#802](https://github.com/orieg/expanse/issues/802) stays open.** Each gate reads three statistics and passes only when all three do. In every run of both pins the scaling and absolute statistics pass — idle `opt/full` `S(7)` is 10.2955–10.3984 and paced `opt/trie` `S(7)` is 3.1185–3.3027 — but O1's and O2's single-reader control fails its non-inferiority floor: with one reader and no writer, `opt` delivers 0.958–0.969 of what `full` and `trie` deliver, and all eight intervals sit entirely below the registered floor of 0.98. O3's control passes (1.2518–1.2549). Closing #802 needs O1 *and* O3 to pass under both pins, so an O3 pass alone does not close it; what follows is the issue's second branch, decided there. O2's `BOUNDARY_RESULT` means no later default proposal may name `kOptimistic` over `kTrieCall` for idle reads. **No default changes here**, and no mechanism is attributed to any ratio — no counter was collected on these runs. Full statistics, the reported-never-gated ratios and the per-scope curves: [`METHODOLOGY.md` §5.17](METHODOLOGY.md#517-outcomes-of-the-optimistic-seek-arm).

Its single-threaded bound is [`scripts/locate_ir_bound.py`](scripts/locate_ir_bound.py) in the `rocksdb-locate-ir-bound` CI job, and its soundness gates are `integrations/rocksdb/tests/test_differential_memtable.cc` (G-O1), `test_expanse_memtable.cc` (G-O2) and `test_memtable_park_points.cc` (G-O3–G-O6). Its counters, reported and never gated, are the `rocksdb_concurrent_optimistic_counters` suite (`scripts/bench_counters.py`, cells `rocksdb_opt_paced_*`).
- Hardware counters: [`scripts/bench_counters.py`](../../../scripts/bench_counters.py) cells `rocksdb_conc_{idle,paced}_r{1,2,7}` attach `perf stat --per-thread` to the concurrent harness's counters mode (`--arm expanse --rounds N --wait-stdin`), and add a `perf c2c` round on the two `R = 7` cells. Dispatched as the `rocksdb_concurrent_counters` suite, once per `cpu_pin`. Diagnostic only: nothing is gated on a counter. These are the frozen inputs of the narrowed-mutex arm, dispatched as the `rocksdb_locate_profile` suite.
